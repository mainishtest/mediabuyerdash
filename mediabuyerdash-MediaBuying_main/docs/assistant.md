# AI-Guided Optimization Assistant

Route: `/assistant`
Phase 5 feature — an operational Q&A surface grounded in live dashboard data.

---

## What the assistant is for

The assistant helps operators answer operational questions quickly without navigating across multiple dashboard sections. It understands the current state of campaigns, experiments, creative, pacing, approvals, and learnings, and routes users toward the right next action.

It is **not** a general-purpose chatbot. It is **not** connected to the public internet or external knowledge bases. All responses are grounded in data pulled from existing dashboard aggregations.

---

## What data it uses

The assistant assembles context from three existing aggregators in parallel:

| Source | Data provided |
|---|---|
| `buildCommandCenterPayload()` | Priority queue, alerts, approvals, experiments, creative items, pacing status |
| `buildExecutiveSummary()` | KPI cards with deltas, period narrative (headline, what happened, what worked, etc.) |
| `queryLearningMemory()` | Top 15 learning entries (experiment outcomes, campaign patterns, creative insights) |

**Important attribution rules applied:**
- ROAS and CPA are sourced from CRM (not Meta delivery)
- Attribution window: 7 days
- Dayparting analysis uses the ad account timezone
- Spend figures come from Meta delivery data
- Revenue figures come from Shopify/CRM reconciliation

## Supported question types (intents)

The assistant classifies each question into one of 10 intents:

| Intent | Example questions |
|---|---|
| `summarize_account_state` | "What happened this week?", "Give me a summary" |
| `explain_performance_drop` | "Why is ROAS dropping?", "What's causing the decline?" |
| `identify_goal_risk` | "Which campaigns are at goal risk?", "Who's off target?" |
| `recommend_next_actions` | "What should I work on today?", "What's my priority?" |
| `explain_winner` | "Which campaign had the best results?", "What worked?" |
| `explain_loser` | "What's underperforming?", "Worst campaigns?" |
| `summarize_creative_fatigue` | "Which creatives need refreshing?", "Any ad fatigue?" |
| `summarize_experiment_status` | "What experiments are running?", "Any experiment winners?" |
| `identify_pending_approvals` | "What approvals are waiting?", "What needs sign-off?" |
| `find_highest_priority_issue` | "What's most urgent?", "What's on fire?" |

Questions that don't match a clear intent fall back to `find_highest_priority_issue`.

---

## How responses stay grounded

Responses have two parts:

1. **Summary text** — generated by Claude (Anthropic API) using a system prompt that instructs the model to only use the provided data context, cite sources, and not fabricate metrics. If the Anthropic API is not configured (`ANTHROPIC_API_KEY` not set), a template-based response is used instead — it is built from real data programmatically.

2. **Evidence, entities, and action links** — built **deterministically** from the context data using pure functions. These are not generated by the LLM. They always reflect actual data from the aggregators.

This architecture means even without an AI API key, the assistant returns grounded, data-linked responses.

## Architecture

```
User question
    ↓
classifyOptimizationAssistantIntent()  (keyword scoring, pure function)
    ↓
buildOptimizationAssistantContext()    (parallel: command center + executive + learning memory)
    ↓
    ├── summarizeAssistantEvidence()   (deterministic from context)
    ├── buildOptimizationAssistantEntityReferences()  (deterministic)
    ├── buildOptimizationAssistantActionLinks()       (deterministic)
    ├── buildOptimizationAssistantSuggestions()       (deterministic)
    └── buildOptimizationAssistantResponse()          (calls Anthropic or template)
    ↓
OptimizationAssistantResponse → client UI
```

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | Optional | LLM-based summary generation. Falls back to templates if absent. |
| `ANTHROPIC_MODEL` | Optional | Override model (default: `claude-haiku-4-5-20251001`) |

The assistant is fully functional without an API key — template responses are grounded in real data.

## Current limitations

- **No persistent session storage** — conversation history lives in component state and is lost on page refresh. This is intentional for Phase 5 (no new Prisma tables).
- **Context window covers 30 days by default** — adjust via the date filter.
- **Intent classification is keyword-based** — complex or ambiguous questions may not be classified precisely; the default fallback is `find_highest_priority_issue`.
- **Response latency** — the context assembly step calls three aggregators in parallel. On cold start this may take 2–5 seconds. LLM generation adds 1–3 seconds if the API is configured.
- **No autonomous execution** — the assistant surfaces action links but does not execute any write operations. Approvals, budget changes, and campaign actions require user navigation to the relevant workflow surface.
- **Campaign-level detail** — the assistant works at account/client level. For individual campaign deep-dives, use the Optimization page directly.

## Upgrading to a strategy copilot (Phase 6)

The architecture is designed for forward extension:

1. **Persistent sessions** — add `AssistantSession` and `AssistantMessage` Prisma models; swap `useState` history for DB-persisted thread.
2. **Streaming responses** — replace `POST /api/assistant` response with a streaming `ReadableStream`; update UI to stream text tokens.
3. **LLM-based intent classification** — replace keyword scoring with a structured output Claude call for improved accuracy on complex questions.
4. **Plan generation** — add a `generate_action_plan` intent that produces a structured list of recommended actions rather than a single summary paragraph.
5. **Richer context** — add campaign-level Prisma queries to `contextAssembler.ts` for deeper per-campaign drill-down.
